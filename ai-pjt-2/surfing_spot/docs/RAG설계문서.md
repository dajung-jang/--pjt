# RAG 파이프라인 설계문서 — Surf Lab

## 1. 전체 흐름

```
[사용자 질문 + 선택한 해변]
        │
        ▼  (app.py: prepare_docs)
 ① 검색어 추출 (프롬프트 1)  ── 항목 자체 검색어("시군구 이름 해수욕장")는 항상 추가
 ② 위키 검색 → 후보(제목+요약)
 ③ 후보 선별 (프롬프트 2)    ── 본문을 받기 전에 버릴 문서를 정해 호출 수를 줄임
 ④ 본문·원문 URL 수집 → data/cache/docs/ 저장, 검색어 캐시 기록
 ⑤ 청킹 → surf_docs 색인
        │
        ▼  (graph.py: LangGraph)
 retrieve ── 메타 청크 1건(항상) + 문서 청크 Top-k(범위: 선택 항목 + common) → 병합·중복 제거 → 근거 번호 부여
        │
 generate ── 프롬프트 3 → 답변 → 근거 없는 문장의 번호 제거(citations.py)
        │
        ▼  (app.py)
 답변 + "답변에 사용한 근거"(인용된 번호만, 유형 라벨·제목·원문 링크)
```

수집·색인(①~⑤)은 시간이 걸리고 진행 상태를 보여줘야 해서 LangGraph 앞에서 화면이 처리하고, 그래프는 "이미 색인된 자료로 답하는" 두 노드만 맡는다.
수집이 실패해도 이미 색인된 자료로 이어서 답한다.

## 2. Vector DB 컬렉션과 메타데이터

두 컬렉션은 성격이 달라 분리했다. 메타데이터는 항목당 1건이라 검색 없이 항상 넣고, 문서 청크는 수가 많고 범위 필터가 필요하다.

| 컬렉션 | 내용 | 청크 id | 메타데이터 필드 |
|---|---|---|---|
| `surf_meta` | 항목 메타데이터, 항목당 1청크 (277건) | 항목 id (예: `spot_001`) | `item_id`, `name`, `region`, `type` |
| `surf_docs` | 위키 문서 청크 | `범위:문서ID:순번` (예: `common:wiki_123:0`) | `scope`, `doc_id`, `doc_key`, `title`, `url`, `source_type`, `kind`, `query`, `related_item_id`, `related_item_name`, `collected_at`, `chunk_index` |

- **`scope`** 가 검색 범위 필터다. 항목 자체를 다룬 문서는 그 항목의 id, 공통 개념 문서(서핑·파도·이안류 등)와 질문에서 선별된 문서는 `common`. 이 필드가 없으면 다른 해변의 문서가 근거에 섞인다.
- **청크 id에 범위를 포함**해서 여러 항목이 같은 문서를 수집해도 서로 덮어쓰지 않는다. 같은 문서를 다시 색인할 때는 `doc_key`(`범위:문서ID`)로 옛 청크를 지우고 넣기 때문에 청크 크기를 바꿔도 예전 청크가 남지 않는다.
- Chroma 메타데이터는 `None` 을 받지 않아 빈 값은 빈 문자열로 저장한다.
- 항목 id 로 `surf_meta` 를 덮어쓰기 때문에 색인을 다시 실행해도 건수가 늘지 않는다.

## 3. 문서 수집·청킹·색인 흐름

1. **공통 문서**: `collector.py --common` 이 `data/wiki_docs.json` 의 개념 문서(서핑, 서핑의 역사, 서프보드, 파도, 이안류)를 수집한다. 범위는 `common`.
2. **질문별 수집**: 프롬프트 1이 최대 3개(`MAX_QUERIES`)의 검색어를 뽑고, 항목 자체 검색어를 맨 앞에 추가한다. 이미 처리한 검색어는 `queries.json` 에 기록되어 있어 다시 호출하지 않는다.
3. **후보 선별**: 검색어마다 후보 5건(`SEARCH_LIMIT`)의 제목과 요약만 프롬프트 2에 보여 최대 3건(`MAX_SELECT_DOCS`)을 고른다. 선별된 문서가 300자(`MIN_DOC_CHARS`)보다 짧으면 제외한다.
4. **항목 자체 문서 우선**: 항목 이름·지역이 맞는 문서는 선별과 길이 규칙을 건너뛰고 항상 수집한다(최대 2건).
5. **저장**: 본문과 메타데이터를 `data/cache/docs/{범위}__{문서ID}.json` 에 저장한다. 색인과 수집을 분리해 두었기 때문에 청크 설정을 바꿔 다시 색인할 때 위키를 다시 부르지 않는다.
6. **청킹·색인**: `RecursiveCharacterTextSplitter`(크기·중복은 `config.py`)로 나누고 `surf_docs` 에 넣는다. 색인에 없는 저장 문서는 앱이 질문할 때 자동으로 복구한다(`sync_docs_index`).

## 4. 검색 결과 병합과 중복 제거

1. 선택한 항목의 메타 청크 1건은 검색 없이 항상 근거 1번으로 넣는다. (`surf_meta` 에서 id 로 조회)
2. `surf_docs` 를 질문으로 검색한다. 필터는 `scope ∈ {선택 항목 id, common}`. 기본은 유사도 검색 Top-k(`TOP_K_DOCS`=5), `USE_MMR=True` 면 후보 `MMR_FETCH_K`건을 가져와 다양성 기준으로 k건을 고른다.
3. 두 결과를 `메타 → 문서 순서`로 합치고 `doc_key:chunk_index` 가 같은 청크는 한 번만 남긴다.
4. 앞에서부터 근거 번호 1, 2, 3…을 붙인다. 이 번호가 프롬프트의 `[근거 N]`, 답변 본문의 표기, 화면의 근거 목록에서 같은 번호로 쓰인다.
5. 문서 검색이 실패해도 메타 근거 1건은 남기고 오류는 터미널 로그에만 남긴다(화면에는 내보내지 않는다).

## 5. 프롬프트

| 번호 | 역할 | 입력 | 출력 형식 | 핵심 제약 |
|---|---|---|---|---|
| 1 검색어 추출 | 서핑·해수욕장 안전에 밝은 서핑 강사 겸 해양 지식 전문가 | 해변, 질문 | JSON 문자열 배열 | 해변 이름은 코드가 따로 검색하므로 넣지 않음, 위키로 답할 수 없는 질문이면 `[]` |
| 2 후보 선별 | 같은 전문가 | 해변, 질문, 후보 제목+요약(100자) | 번호의 JSON 정수 배열 | 이름만 같은 다른 지역·동음이의 제외, 애매하면 고르지 않음. 본문을 받기 전에 걸러 외부 호출을 줄임 |
| 3 답변 생성 | 같은 전문가 | 해변, 번호 붙은 근거(유형 라벨 포함), 직전 대화 6개, 질문 | 한국어 답변 + `[근거 N]` | 근거만 사용, 없으면 "제공된 자료에서는 확인되지 않는다", 비어 있는 항목 속성 추측 금지, 실시간 정보는 모른다고 답하고 현장 확인 안내, 번호 범위 표기 금지 |
| 4 입수 판단 가이드 | 서핑 강사 겸 해양 안전 전문가 | 사용자가 입력한 조건, 근거 | 세 소제목 구조 | 근거 없는 수치 기준 금지, "안전하다" 단정 금지 |
| 5 조건 항목 선별 | 서핑·해수욕장 전문가 | 조건, 후보 항목 정보 | 번호의 JSON 정수 배열 | 항목 정보에 적힌 내용으로만 판단, 없는 특징은 추측하지 않음 |

프롬프트 1~3이 필수 3종이고 4·5는 서비스 기능(F2010, F2011)을 위해 추가했다.
JSON 응답은 코드가 파싱하며(`parse_query_list`, `parse_index_list`), 범위 밖 번호·중복·형식 오류는 버린다.

## 6. 청크 크기, 중복 길이, 근거 수(Top-k)

| 설정 | 값 | 이유 |
|---|---|---|
| `CHUNK_SIZE` | 1000자 | 명세 예시 값에서 시작. 위키 문서의 한 절이 한 청크에 들어가는 크기 |
| `CHUNK_OVERLAP` | 200자 | 문장·절이 경계에서 잘려 의미가 끊기는 것을 줄임 |
| `TOP_K_DOCS` | 5 (+ 메타 1건) | 근거를 너무 많이 넣으면 프롬프트가 길어지고 관련 없는 청크가 섞임. 메타 1건은 항상 별도로 포함 |
| `MMR_FETCH_K` | 30 | MMR 사용 시 후보를 넉넉히 가져온 뒤 다양성으로 고름 |

### 값을 바꿨을 때의 차이 (실측)

같은 저장 문서 5건(서핑, 서핑의 역사, 이안류, 파도, 서프보드)을 다시 색인한 결과. (빈 청크 필터와 참고문헌 구역 제거를 적용하기 전 측정이다. 적용 후 저장 문서 9건 기준 1000/200 설정은 **36건**이다.)

| 크기 / 중복 | 청크 수 | "이안류 대처" 검색 상위 3건 |
|---|---|---|
| 1000 / 200 | **33건** | 이안류(청크 0), 파도(청크 5), 파도(청크 4) |
| 500 / 100 | **76건** | 파도(청크 8), **이안류(청크 1 — "해류를 탔을 경우 대책")**, 이안류(청크 0) |

- 청크를 줄이면 대처법 절이 따로 잡혀 질문에 직접 맞는 청크가 상위에 올라왔다. 반면 청크 수가 2.3배 늘고 한 청크가 담는 맥락은 줄었다.
- 이안류 문서(646자)는 1000자 설정에서는 청크 1건이라 문서 전체가 한 번에 들어가 대처법이 다른 내용과 함께 전달된다.
### Top-k 와 MMR 을 바꿨을 때의 차이 (실측, `docs/03_검증결과.md` 6장)

- **Top-k**: "이안류에 휘말리면 어떻게 해?"에서 k=3 / 5 / 8 은 근거가 4 / 6 / 9건이다. 대처법이 담긴 이안류 청크는 k=3 에서도 들어와서, k 를 늘리면 인명구조원 문서처럼 관련 있는 근거가 추가되지만 무관한 청크도 같이 늘었다. 그래서 기본값 5(메타 1건 + 문서 5건)로 두었다.
- **MMR**: "파도에 대해 알려줘"에서 유사도 검색은 같은 문서(파도) 청크가 4건 몰렸고, MMR 은 문서가 더 다양해졌지만 관련 낮은 청크가 섞이고 상위 청크 하나가 빠졌다. 한 해변·한 주제를 묻는 질문이 많아 기본값은 유사도 검색이다.
- **발견한 문제**: 소제목뿐인 청크와 참고문헌 목록 청크가 근거 자리를 차지했다. 색인할 때 소제목을 뺀 본문이 50자(`MIN_CHUNK_CHARS`) 미만이면 색인하지 않고, 문서 끝의 참고문헌·외부 링크 구역은 잘라 내도록 고쳤다. 적용 후 청크 수는 38건 → 36건(저장 문서 9건 기준)이다.

## 7. 근거 표시 방식

1. 프롬프트 3이 근거 문장 뒤에 `[근거 N]`, 여러 개면 `[근거 1, 3]` 형태로 쓰게 한다.
2. 화면은 정규식으로 번호를 찾아 **실제로 인용된 근거만** "답변에 사용한 근거 N건"에 표시한다.
3. 각 근거는 `[근거 N] 유형 라벨 제목 · 원문 링크` 로 보인다. 유형 라벨은 "항목 메타데이터" 또는 "위키백과"(출처 종류)다. 항목 메타데이터는 원문 링크가 없어 출처 이름(공공데이터포털 …)을 대신 보여준다.
4. 인용된 번호가 하나도 없으면 "ⓘ 답변에 인용된 근거가 없습니다."를 안내한다.
5. **후처리(`citations.py`)**: 모델이 "확인할 수 없다"는 문장에까지 `[근거 1, 2, 3]` 을 붙이는 경우가 있어, 그런 문장의 번호는 문장 단위로 지운다. 실제 내용을 말하는 문장의 번호는 그대로 둔다.

## 8. 도메인 특화 기능(입수 판단 가이드)을 이렇게 설계한 이유

서핑에서 가장 위험한 판단은 "오늘 들어가도 되는가"이다. 그런데 이 서비스는 실시간 정보를 가지고 있지 않다.
그래서 (1) 현장에서 본 조건을 **사용자가 입력**하게 하고, (2) 서비스는 판단을 대신하지 않고 **색인된 문서에서 근거를 찾아 고려사항만 정리**하며,
(3) 근거에 없는 것은 "확인되지 않는 부분"으로 분리해 보여주도록 했다. 위키에 숙련도별 파도 기준이 없는 지금은 이 칸이 길어지는데, 그것이 오히려 정직한 결과다.
(4) 입수 통제·경보가 있다고 체크하면 LLM을 거치지 않고 입수하지 말라는 고정 안내만 나온다. 위험 신호에 모델 판단을 끼우지 않기 위해서다.

## 9. 선택한 이유, 겪은 문제, 해결 과정

| 주제 | 선택/문제 | 해결 |
|---|---|---|
| 도메인 데이터 | 서핑 전용 공개 데이터가 거의 없음 | 공공데이터포털 해수욕장 277건을 항목으로 쓰고 서핑 스팟 4곳은 유형을 표시. 난이도 등 출처 없는 속성은 비워 둠 |
| 중복 키 | 이름만으로 중복 제거하자 "송정"이 3개 지역에서 하나로 합쳐짐 | `(이름, 지역)` 을 키로 변경 |
| 위키 정보 부족 | 죽도·인구·중문색달은 위키 문서 없음, '서핑' 문서에 한국·안전 정보 없음 | 공통 개념 문서 + 항목 자체 문서 구조로 설계, 해변 단위 안전 정보는 PDF(F2016)로 확장 가능하게 남김 |
| 수집과 색인 결합 | 청크 설정을 바꿀 때마다 위키를 다시 불러야 함 | 문서 본문을 `data/cache/docs/` 에 저장하고 색인과 분리 |
| 모델이 인용 규칙을 어김 | "확인할 수 없다"는 문장에도 `[근거 1~6]` 표기, `~` 가 마크다운 취소선으로 렌더링 | 프롬프트에 규칙 추가 → 사용자 메시지 끝에도 규칙 반복 → 그래도 어겨 코드 후처리(`citations.py`)로 해결 |
| 이안류 문서가 근거에서 빠짐 | `chroma_db` 가 비었는데 앱이 저장된 문서를 다시 색인하지 않고 검색 오류도 삼킴 | `sync_docs_index` 로 저장 문서를 자동 복구, 검색 실패는 터미널 로그에 남김 |
| 항목 전환 시 대화 혼선 | 대화 기록이 하나라 다른 해변의 대화가 프롬프트에 섞일 수 있음 | 항목 id 별 대화 기록으로 분리 |

# 05-pjt : 댓글 증강 시스템 (토스증권 댓글 크롤링 + LLM 데이터 증강)

Django 웹 애플리케이션에서 사용자가 입력한 회사명을 기준으로 토스증권 커뮤니티 댓글을 실시간 크롤링하고, 전처리 → LLM 증강 → 통합 출력까지 수행하는 서비스입니다.

## 1. 실행 방법

```bash
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
```

프로젝트 루트에 `.env` 파일을 만들고 GMS 키를 작성합니다. (Git에는 포함하지 않음)

```
GMS_KEY=발급받은_키
```

```bash
python manage.py migrate
python manage.py runserver
```

- 접속: http://127.0.0.1:8000/
- Chrome 브라우저 필요 (Selenium이 자동으로 실행)
- 회사명 검색 시 Chrome 창이 자동으로 열리며, 크롤링과 LLM 호출로 30초~1분 정도 소요됩니다. (창을 닫지 말고 기다려 주세요)

| F603 | 회사 검색 및 선택 | `/` 단축키로 검색창을 열어 검색, 최상단 결과 자동 선택, 검색 중 "댓글 수집 중..." 진행 상태 표시 |

| F607 | 데이터 통합 | 원본 / 전처리 / 증강 / 최종 결과를 4개 컬럼으로 구분 출력하고 DB에 저장 |
| F610 | 댓글 요약 | 수집된 전체 댓글을 LLM으로 요약해 하단에 출력 |
| F611 | 예외 안내 | 회사 검색 결과가 없거나 댓글이 없으면 안내 메시지 출력 |

### 처리 흐름

```
입력(F601) → 회사 검색(F603) → 댓글 수집(F604) → 전처리(F605)
          → 증강(F606) → 통합·DB 저장(F607) → 요약(F610) → 화면 출력
```

### 구현 포인트

- 크롤링, 전처리, LLM 호출을 `crawler.py`, `preprocess.py`, `llm.py`로 분리해 각 단계를 독립적으로 테스트할 수 있게 구성했습니다.
- LLM 응답이 JSON 형식이 아니거나 호출이 실패해도 서비스가 중단되지 않도록 예외 처리했습니다. (부적절 필터 실패 시 필터 없이 진행, 증강 실패 시 원문 사용)
- 회사 검색 실패와 댓글 없음을 별도 예외(`CompanyNotFound`, `NoComments`)로 구분해 사용자에게 상태를 안내합니다.
- GMS API 키는 `.env`로 관리하고 `.gitignore`에 등록해 저장소에 올라가지 않도록 했습니다.
- IQR 임계값은 원본 댓글 길이를 기준으로 계산해 DB에 저장했습니다. (길이 필터는 명세의 5~76 기준을 그대로 사용)

## 5. 학습 내용

### 1) 동적 페이지에서 검색창 입력이 동작하지 않던 문제
처음에는 검색창을 클릭하고 입력한 뒤 Enter를 누르는 방식으로 구현했는데, 종목 페이지로 이동하지 못해 "회사를 찾을 수 없음" 상태로 끝나는 문제가 있었습니다. 원인을 짐작만 하며 코드를 고치는 데 한계가 있어, 토스증권에서 정상 동작이 확인된 크롤링 코드를 참고해 구조를 다시 잡았습니다.

- `/` 단축키로 검색 모달을 여는 방식
- `placeholder`로 입력창을 찾는 방식
- `WebDriverWait`로 요소가 나타날 때까지 기다리는 방식

이 과정에서 클래스 이름은 사이트 배포 때마다 바뀔 수 있으므로, `aria-label`, `placeholder`, 스타일 속성처럼 **역할을 나타내는 속성**을 기준으로 선택자를 잡는 것이 더 안정적이라는 것을 배웠습니다.

### 2) shell에서는 되는데 서버에서는 실패한 `StaleElementReferenceException`
Django shell에서 크롤러를 테스트할 때는 정상이었는데, `runserver`에서 실행하면 `StaleElementReferenceException`이 발생했습니다. 스크롤할 때마다 댓글 목록이 다시 그려지기 때문에, 처음에 찾아둔 스크롤 영역 요소가 무효가 된 것이 원인이었습니다. 이를 해결하기 위해 다음과 같이 수정했습니다.

- 스크롤 영역을 반복마다 새로 찾도록 변경
- 사라진 요소를 읽을 때 발생하는 예외는 건너뛰도록 처리
- 클릭이 막히는 경우를 대비해 JS로 직접 스크롤하도록 보강

같은 코드라도 실행 환경과 타이밍에 따라 결과가 달라질 수 있다는 점을 알게 되었습니다.

### 3) 종목명이 잘못 읽히던 문제
실제종목명이 처음에는 입력값인 "삼성"으로 출력되었고, 이후 웹 화면에서는 현재가인 "217,750원 -6.14%"가 종목명으로 읽혀 화면 제목과 DB에 그대로 저장되는 문제가 있었습니다. 종목번호가 있는 요소 근처의 텍스트를 가져오는 방식이었는데, 화면이 다 그려지기 전이거나 가격 텍스트가 같이 잡히는 경우가 있었기 때문입니다.

- 종목번호 요소가 나타날 때까지 대기
- 가격(`원`), 등락률(`%`), 숫자만 있는 줄은 제외하고 이름 줄만 선택
- 모두 실패하면 페이지 제목, 입력값 순으로 대체

크롤링한 값은 **저장하기 전에 직접 출력해서 확인**해야 한다는 것을 배웠습니다.

### 4) 입력값이 없을 때 동작하지 않는 것이 정상이라는 점 (F601)
빈 칸으로 검색했을 때 화면이 바뀌지 않아 오류인지 헷갈렸지만, 명세의 "입력값이 없는 경우 아무런 동작을 수행하지 않는다"는 요구사항대로 동작하는 것이었습니다. 템플릿의 JS에서 제출을 막고, view에서도 `strip()` 후 빈 값이면 아무 작업을 하지 않도록 이중으로 처리했습니다. 개발자가 보기에 변화가 없는 것도 올바른 동작일 수 있으며, 로그(`runserver` 터미널)로 확인할 수 있다는 것을 알게 되었습니다.

### 5) 그 밖에 배운 점
- **Django 요청 흐름**: URL → view → template 구조를 익혔고, GET 방식 폼으로 입력을 받아 view에서 크롤링·가공·출력까지 처리하는 흐름을 구현했습니다.
- **LLM 활용**: 프롬프트에 출력 형식(JSON 배열)과 개수를 명시하고, 응답을 정규식으로 파싱해 실패에 대비했습니다. LLM의 부적절 댓글 판정은 호출마다 조금씩 달라질 수 있다는 점도 확인했습니다.
- **환경 분리**: `.env`와 `python-dotenv`로 API 키를 코드와 분리했습니다.
- **단계별 디버깅**: 크롤러, 전처리, LLM을 shell에서 각각 테스트한 뒤 통합하니 원인을 찾기가 훨씬 쉬웠습니다.

## 6. 느낀 점

처음에는 크롤링이 요소를 찾아 텍스트를 가져오는 단순한 일이라고 생각했다. 하지만 검색창 입력이 먹히지 않아 막혔을 때, 어디서 어긋났는지 눈으로 보이지 않아 추측만으로는 해결이 어렵다는 것을 느꼈다. 정상 동작이 확인된 코드를 참고해 구조를 바꾸면서, 선택자를 어떤 기준으로 잡아야 하는지와 요소가 나타날 때까지 기다리는 타이밍이 얼마나 중요한지 알게 되었다.

shell에서는 잘 되던 코드가 서버에서 `StaleElementReferenceException`으로 실패했던 경험도 기억에 남는다. 같은 코드라도 실행 환경과 타이밍에 따라 결과가 달라질 수 있고, 한 번 성공했다고 끝이 아니라는 것을 배웠다. 종목명이 "삼성"과 "217,750원"으로 잘못 나왔을 때는 결과를 화면과 DB에 반영하기 전에 값을 직접 확인하는 습관이 필요하다고 느꼈다.

또 빈 입력에서 아무 변화가 없는 것이 오류가 아니라 요구사항대로의 동작이었던 일을 통해, 기능이 "동작하지 않는 것"도 명세에 맞는 결과일 수 있음을 알게 되었다. LLM도 결과를 그대로 믿지 않고 형식 검증과 실패 시 대체 동작을 만들어 두어야 한다는 것을 느꼈다.

앞으로는 검색하면 제일 처음 나오는 결과를 자동으로 선택하는 방식이 아니라, 검색 결과 리스트에서 사용자가 직접 선택해 댓글을 크롤링하는 기능으로 개선해 보고 싶다.
